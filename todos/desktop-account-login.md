## 第一项：应用配置与 Runtime 合约

应用注册配置在 Runtime 启动时读取并固定，优先级为启动环境变量 `ANVIL_MICROSOFT_CLIENT_ID`、同名构建环境变量、仓库既有默认公开 ID。配置错误不使整个 Runtime 退出，配置查询返回明确原因；这里检查的是 ID 格式，不代表 Microsoft/Minecraft 已接受该应用的授权请求。

| 接口 | 请求与返回 |
| --- | --- |
| `GET /accounts/login` | `{ enabled, unavailableReason }`，目前不可用原因为 `invalid_client_id`，可用时原因为 `null`。 |
| `POST /accounts/login` | 无需 Client ID 或请求体，返回 202 和登录操作快照；有进行中的授权时返回 409。 |
| `GET /account-operations/active` | 返回 `{ operation }`；没有运行中操作时为 `null`，用于恢复启动响应丢失或 409 冲突后的既有操作。 |
| `GET /account-operations/{id}` | 查询操作；不存在或已清理的历史操作返回 404。 |
| `DELETE /account-operations/{id}` | 请求取消并返回当前快照；清理结束前仍为 `running`，不要当成已经取消成功。 |

快照字段：`id`、`state`、`stage`、`cancelRequested`、`authorization`、`account`、`error`。`state` 为 `running/completed/failed/cancelled`；`stage` 为 `requesting_code/waiting_for_approval/checking_profile/saving_account`。

- `authorization` 仅在等待授权时包含展示用验证码和验证地址；等待事件不会覆盖验证码。`expiresAt` 是 Unix 秒时间戳，`pollIntervalSeconds` 是 Core 向 Microsoft 查询的间隔，不要求 UI 以同样间隔查询本机状态。
- 接受取消时，立即设置 `cancelRequested=true` 并清除 `authorization`；清理期间的排队事件不能重新显示验证码。Core 清理完成后才进入 `cancelled`，重试应等待终态。
- 进入 `saving_account` 是提交边界，开始保存后不再接受取消，操作等待保存后返回实际结果，避免界面宣称取消成功而磁盘已新增账户。
- 取消或保存失败时，仅清理未保存的新账户凭据；已有账户的新凭据不因本次操作失败被删除。清理失败保留错误信息，不伪称清理已完成。
- 所有终态清除验证码；快照不含 Microsoft device token、OAuth/Minecraft access token 或 refresh token。终态账户仅有公开 ID、游戏名和选中状态。

## 第二项：窗口账户状态

- `account-state.svelte.ts` 使用 Svelte 响应式状态持有公开账户列表、当前账户、加载/变更状态、配置及瞬时登录快照；`account-provider.svelte` 在窗口范围提供上下文并负责销毁。组件不自行保存令牌或登录资料到 localStorage。
- 窗口挂载时读取一次账户，之后仅按用户操作刷新；页面切换保持同一份状态。账户菜单复用该状态，继续保留现有紧凑样式。
- 加载、切换及登出防止重复提交；出错保留上次已知列表。重试变更前先重新读取实际账户，避免在服务端已经切换/移除账户但响应丢失时重复操作；再次读取失败保留原始重试目标。
- `startLogin/loadLoginConfiguration/cancelLogin/resumeLogin/resetLogin` 为下一项弹窗提供操作。申请验证码必须由显式登录动作触发，初始化和打开账户菜单不会开始授权。
- 本机进度查询采用前次请求结束后再等待 1.2 秒的方式；不会用 interval 叠加请求。查询失败暂停并保留操作 ID，用户可显式恢复；任务 404 则结束旧流程并允许重新登录。
- 登录启动响应丢失或 409 时，通过鉴权后的活动操作接口接回已有任务。取消会中止旧的进度请求并清除验证码，旧响应不会覆盖新状态；已接受的取消仅查询清理进度直到终态。保存提交阶段不再发出取消。
- 登录完成后立即合入 Runtime 返回的账户并再刷新完整列表；刷新失败不会抹掉已确认的成功身份。保存的公开身份不被解释为已验证的长期有效会话。
- Provider 销毁时清除定时器、中止读取并忽略旧响应；对未进入保存阶段的已知登录任务尽力请求取消。启动请求仍在途中时，收到操作 ID 后再取消，避免只取消页面请求而遗留授权操作。窗口进程直接关闭时的最终清理仍由 Runtime 生命周期负责。

检查：2026-10-22 前端静态检查（0 错误、0 警告）、生产构建、Runtime 离线编译及 Rust 格式检查通过。通过临时编译实际状态模块并替换 API 的方式，完成 18 个隔离 fixture 场景：重复请求、变更响应丢失后的恢复、取消期间的旧进度响应、启动期间取消/销毁、轮询失败/404、409 恢复、配置不可用、终态重置和不重叠查询等。fixture 不访问网络或系统凭证库，临时文件已清理；真实登录和 WebView 中的登录弹窗仍待后续联调。
