# Shell 与 Desktop 兼容性

## 已实现

- Shell API 默认从 1.0.0 增加到 1.1.0，产品版本未变更。Desktop 的最低范围继续为 ^1.0.0：新增字段都是可选读取，兼容旧 Shell 的已有功能。
- `shell_get_app_info` 新增 capabilities，列出实际实现且具有原生权限的功能。当前包含窗口主题、App/Shell 更新、打开日志目录和外部 URL；没有窗口材质切换权限，不宣称支持 window.effects。
- Desktop 能力助手优先读取显式清单；缺少清单时仅对已知 1.0.0 合约提供基线能力，其他未知能力/版本不猜测。原生主题同步已使用能力助手，无额外后台轮询。
- 包的 schema、身份、平台、版本、入口和 API 范围格式先验证。真正的 Shell 版本不满足返回 `shell_upgrade_required`，附带 requiredShellApi；格式错误、错误签名和损坏包保留原错误。
- 不兼容时不发布/启用下载包，不改 active/pending 状态，也不标记为已启动失败。当前版本继续使用；后续升级 Shell 后仍可重试同一 Desktop 更新。
- 导航更新入口提示先更新启动器，进入“设置 → 关于”；关于页提供说明与安装包链接。优先使用经 Shell 校验的更新链接；无可用链接时进入项目 Releases，不执行安装器、不强制重启。

## 维护约定

1. 普通业务/UI 改动不要求升级 Shell。
2. 新增可选原生能力：Shell 实现、授予权限并公布 capability，Desktop 检测后才显示/调用，不把 IPC 异常当成功。
3. 新增必需原生能力：提高 Shell API minor，并提高 Desktop manifest 的最低范围（如 ^1.1.0）；破坏性协议变更提高 major。
4. 能力声明必须通过原生权限一致性检查。能力表示接口存在，不表示更新源已配置或目标操作必定成功。
5. 不扩大旧签名 feed 字段；已有 Shell 的严格解析器不认识新字段。当前兼容性识别发生在经过摘要校验的包解压之后，不是下载前筛选，也不从未签名远端数据决定版本要求。

## 旧版本与验收边界

已发行 Shell 1.0 仍会拒绝不兼容包，但可能只显示通用失败；无法通过新 Desktop 页面更改已经安装的原生检查逻辑。用户安装一次带本改动的新启动器后，才获得明确的更新原因。未新增强制升级，不改公开标签或现有附件。

隔离回归覆盖：合法 ^1.1.0 包对 1.0/1.1 的不同结果；非法范围不误报升级；已签名的本地 HTTP fixture 下载后发现不兼容，旧活动版本和 pending 保持不变；capabilities 与实际权限一致；旧 Shell 回退和显式能力缺失；UI 提示的错误分类。没有访问真实更新源、真实用户数据或账户，也未运行安装器。原生 WebView 的提示与重装后重试需维护者验收。
