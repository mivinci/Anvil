# AI 协作说明

这里记录 Anvil 维护者明确表达并确认的长期偏好，供不同 AI 接续开发。它不是当前任务清单；产品架构见 [architecture.md](architecture.md)，阶段进度和验收见 `todos/`。

## 沟通与推进

- 默认使用中文，技术术语、API 和代码标识保留原文。说明直接、具体，并区分实现状态、验证结果和限制。
- 按用户确认的执行项逐项推进。用户要求每项完成后停下来确认下一项时，完成后就停；遇到会改变结果的阻塞问题，说明证据并提出具体问题。
- 用户已经确认的方案和动作直接执行，不重复征求确认；不要把“继续”解释成切换目标。
- 开始设计或改代码前阅读相关 README、todo 与实际实现。todo 是计划和状态记录，不能代替代码证据。
- 维护设计文档的整体逻辑，不写对话流水账；优先更新同主题文档。

## 架构与实现

- 保持 Cargo workspace crate 职责清楚：`anvil-core` 放公共业务逻辑，`anvil` 负责 CLI，`apps/anvil-shell/src-tauri` 负责 Tauri 桌面宿主。桌面前端在 npm workspace 内维护，并复用 core，不重复实现业务规则。
- core 不依赖 UI 框架、CLI 参数解析或入口创建的 Tokio runtime。由入口创建并持有自己的 Tokio runtime。
- 复用固定版本的 Q2Q `q2q-http` 下载、并发、校验和恢复能力；不要在 Anvil 再造 HTTP 下载器或恢复格式。
- 资源按需使用：避免空闲常驻服务、无界缓存、无界日志和没有明确收益的周期轮询。异步操作应定义进度、取消、清理和最终状态的边界。
- EULA 接受必须是明确决定。真实服务端 smoke 只能使用临时数据目录；默认保持 `online-mode=true`，并将测试服务端限制到 loopback。
- 不把尚未实现的客户端安装/登录、模组加载器、后台服务或 MCP 写成现有功能；先在对应 todo 中完成方案与验收边界。

## Rust、测试与文档

- 遵守仓库根目录 `rustfmt.toml`；Rust 改动运行 `cargo fmt --all -- --check`。
- Core 集成测试放在 `crates/anvil-core/tests/`，CLI 行为测试放在 `crates/anvil/tests/`。优先覆盖公开行为、错误边界、并发、取消、恢复和清理。
- 运行与本次改动相称的验证；清楚报告测试是否使用本地 fixture、真实网络或真实 Minecraft。没运行的测试不能声称通过。
- 普通 CI 使用隔离 fixture。真实 Java/Minecraft 文件验收由维护者在目标平台按需运行 smoke 脚本；CI 不加入真实下载任务，除非用户重新确认。
- 不把令牌、私钥或临时环境绝对路径写入仓库。测试产生的临时目录在结束后清理。

## Git 与交付

- Codex 工作分支使用 `codex/<short-english-description>`；按任务创建分支前确认工作区状态并保留现有改动。
- 用户要求 rebase 时先 fetch `origin/main` 并检查本地历史。未提交文件不能 rebase；没有本地提交时说明并安全地建立远端基线，不能声称执行了提交重放。
- 不向 `main` 推送。用户要求提交到 `codex/` 分支时，将相关提交推送到该分支；不因创建分支而自动创建 PR、合并或发布。
- 汇报本地测试、真实 smoke、远端 CI 和 PR 状态时使用准确的状态词。创建 PR 后附上 PR 链接。

## 如何维护这些约定

长期规则应来自用户明确提出或确认的偏好。一次性实现选择、猜测和临时环境状态留在对应 todo 或执行记录中；新要求与旧规则冲突时，以当前要求为准并同步修订本文档。
